**1)** Пусть на вход дан сигнал x[n], а на выход нужно дать два сигнала y1[n] и y2[n]:

```
 y1[n] = x[n - 1] + x[n] + x[n + 1]
 y2[n] = y2[n - 2] + y2[n - 1] + x[n]
```

Какой из двух сигналов будет проще и быстрее реализовать в модели массового параллелизма на GPU и почему?

Проще будет реализовать y1, потому что все значения x нам уже известны и мы можем параллельно их считывать разными потоками. При вычислении же y2, надо как-то управлять порядком, чтобы y2[i] вычислялся раньше y2[i + 1], это плохо укладывается в модель массового параллелизма, потому что у нас нет никакой гарантии, что i-й поток выполнит свою работу раньше i+1

`Ответ`: y1.

**2)** Предположим что размер warp/wavefront равен 32 и рабочая группа делится
на warp/wavefront-ы таким образом что внутри warp/wavefront
номер WorkItem по оси x меняется чаще всего, затем по оси y и затем по оси z.

Напоминание: инструкция исполняется (пусть и отмаскированно) в каждом потоке warp/wavefront если хотя бы один поток выполняет эту инструкцию неотмаскированно. Если не все потоки выполняют эту инструкцию неотмаскированно - происходит т.н. code divergence.

Пусть размер рабочей группы (32, 32, 1)

```
int idx = get_local_id(1) + get_local_size(1) * get_local_id(0);
if (idx % 32 < 16)
    foo();
else
    bar();
```

Произойдет ли code divergence? Почему?

Заметим, что по условию номер workitem по оси x меняется чаще. Значит idx в одном ворпе будет принимать значения get_local_id(1) + 32 * {0, 1, 2, ...., 31}. Значит в один ворп будут попадать треды с одним и тем же остатком от деления на 32 равным get_local_id(1) и мы всегда будем попадать в один бранч в каждом ворпе и code divergence-а не будет.

`Ответ`: не произойдет.

**3)** Как и в прошлом задании предположим что размер warp/wavefront равен 32 и рабочая группа делится
на warp/wavefront-ы таким образом что внутри warp/wavefront
номер WorkItem по оси x меняется чаще всего, затем по оси y и затем по оси z.

Пусть размер рабочей группы (32, 32, 1).
Пусть data - указатель на массив float-данных в глобальной видеопамяти идеально выравненный (выравнен по 128 байтам, т.е. data % 128 == 0). И пусть размер кеш линии - 128 байт.

(a)

```
data[get_local_id(0) + get_local_size(0) * get_local_id(1)] = 1.0f;
```

Будет ли данное обращение к памяти coalesced? Сколько кеш линий записей произойдет в одной рабочей группе?

Будет, потому что get_local_id(0)  стоит в сумме без множителя, а значит мы будем каждым ворпом обрабатывать 32 подряд идущих элемента data, а значит для каждого ворпа придется подгрузить кеш-линию лишь один раз.

В одной рабочей группе 1024 потока, мы подгружаем по кеш-линии для каждого ворпа. Получаем 1024 / 32 = 32 записи.

`Ответ`: будет. 32 записи.

(b)

```
data[get_local_id(1) + get_local_size(1) * get_local_id(0)] = 1.0f;
```

Будет ли данное обращение к памяти coalesced? Сколько кеш линий записей произойдет в одной рабочей группе?

Не будет, потому что get_local_id(0) идет в индексе в множителем 32. Значит расстояние между двумя соседними потоками в ворпе будет равно 32. А это значит, что на каждую запись будет подгружаться отдельная кешлиния.

`Ответ`: не будет. 1024 записи.

(c)

```
data[1 + get_local_id(0) + get_local_size(0) * get_local_id(1)] = 1.0f;
```

Будет ли данное обращение к памяти coalesced? Сколько кеш линий записей произойдет в одной рабочей группе?

Данное обращение к памяти будет не идеально coalesced. На каждую запись придется подгружать 2 кеш линии, потому что мы имеем дело с выровненными данными. Если в пункте а, мы обращались к идеально выровненным кускам [0, ..., 127], то теперь мы будем обращаться к [1, ...,128] и для 128 элемента придется подгружать отдельную кеш-линию.

Ситуация, аналогичная а, но по 2 кеш-линии на каждую запись. => 64 записи.

`Ответ`: не идеально coalesced. 64 записи.
